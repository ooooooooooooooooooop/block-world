# 《方块长沙》游戏制作方案与实施架构

> 2026-10-16 R13用户澄清：基础架构重点是能复用、能批量更新的制作能力，例如统一字体、批量生成建筑窗户、统一制作地下通道。先学习建模与游戏生产流程，据此建立共同规则和生产能力，再规模铺开与精修；此前逐处精修优先的路线撤回。

初稿：2026-10-15；当前制作方法更新：2026-10-16（R13可复用生产流程；最新游戏源码实现为R11，见台账与对应回执）。依据：[探图与改进台账](探图与改进台账.md)、[实际研究](游戏设计探图记录-20261015.md)、用户的原始要求与路线纠正。此方案是当前有证据支持的制作安排，可由新发现修订；不是穷尽问题的清单。之前按局部修补扩大样板的路线不再默认成立。

## 目标与边界

做一款Minecraft风格的长沙城市游览网页游戏：全长沙连续真实尺度，可从城区步行到远郊；街巷、建筑、地貌、人物与界面形成同一个方块世界，玩家自由游览、观察、拍照和遇见路人。高还原覆盖整个交付城市，既有PRD的85/100、前三维至少80%、关键事实错误零保持。禁止安排真人，不以代理打分冒充真人评价；缺少规定证据时不得宣布该项通过。

用户已指出地址/任务、小地图和快捷栏的游戏内组织。采用它们的功能关系，不能复制广州内容、比例缩小、货币或交通机制。R05已实际验证一次地铁快速传送，仍不证明全市交通准确性，也不替代用户要求的连续步行。建造/破坏、生存战斗、抽卡/收费、多人聊天没有由当前诉求推出，不能因为Minecraft或某个同类游戏有就擅自加入。


## 可复用制作能力与整体生产顺序（R13）

用户所说“一次改一片”对应资产共同定义、参数化生成、模块拼装与统一导入更新。依据[Unity官方生产周期正文](https://learn.unity.com/tutorial/the-real-time-production-cycle?version=2020.3)、[Burgess/Purkeypile的模块化制作经验](https://www.gamedeveloper.com/design/skyrim-s-modular-approach-to-level-design)及[Unreal官方实例更新机制](https://dev.epicgames.com/documentation/en-us/unreal-engine/level-instancing-in-unreal-engine)，结合现有源码，采用以下制作安排。来源及阅读深度见[本轮回执](../artifacts/wuyi-structure-20261016/production-scout-receipt.json)；引擎案例用于理解机制，项目继续使用现有Three.js。

| 生产阶段 | 本项目要产出的能力/内容 | 进入后续工作的依据 |
| --- | --- | --- |
| 1. 前期研究与体验原型 | 真实城市资料、参考游戏体验、美术表达；复用已验证的行走/摄影/人物原型，找出仍影响游览的缺口 | 玩法、实景和制作需求能对应；已有研究不重做，不从空白造一套通用广场 |
| 2. 制作规范与基础管线 | 真实米制/坐标与层位、人物尺寸、部件转轴/接口、命名、像素密度、字体/材质、来源和资源更新规则；性能预算在这里考虑 | 同一资产能从制作进入正式游戏，尺度、材质、身份和来源没有各自一套解释 |
| 3. 常用模块和联合验证 | 共用字体/招牌、立面/窗户、房间/通道/台阶/入口，以及人物骨架/动作等高复用能力；在几种不同尺寸、朝向、层位中检查 | 修改共同定义后所有引用处生效；拼装可回环、可叠层、可变方向；正常行走、摄影和路人通过真实空间检查 |
| 4. 全市批量生产与装配 | 使用真实建筑/道路/地下空间记录驱动共同生成器；资产引用共同资源，各场所参数决定高度、轮廓、开间和连接 | 同类修正从共同规则传播，新增地点主要补事实数据和组合；缺失事实显式保留，不随意补全 |
| 5. 特色内容和整体精修 | 地标独有轮廓、真实商铺、雕塑、庭院、绿化和街具；在共用能力上完成各处还原 | 对照实景在普通游览机位、近中远景与照片中核对；必要的独特形态保留，不能用相同外观替代真实差异 |
| 6. 持续验证、优化与交付 | 跨区长游、保存恢复、照片原件、NPC通行、资源流送/内存/帧时间、启动与打包 | 按原PRD的全市范围与还原标准给出证据；打包后再走普通流程，后续资产更新可重建与回归 |

阶段有依赖但允许交叉迭代。美术/人物/控制与空间需要在第3阶段共同看见效果；不能先把整城做完灰盒才发现表达失效，也不能先精修一处再人工复制成千上万次。五一广场承担真实使用检验；共同模块修好后推广到所有使用处，样板本身不替代全市交付。

| 用户的例子 | 应建立的共同能力 | 如何证明可复用 |
| --- | --- | --- |
| 一次修改所有字体 | 共同字库、字体角色/字号规则与文字绘制接口，覆盖HTML/CSS、地图Canvas和3D招牌；已有本地字库保留，梳理分散字体声明与纹理重建 | 改一个共同字体定义，HUD/大地图/小地图/场景招牌在重新生成后同时生效；只改CSS不算覆盖场景文字 |
| 一次给大楼贴窗户 | 共用立面材质/UV映射、窗框/门/转角部件及沿轮廓生成规则；建筑记录提供高度/层数/开间/样式参数，近处几何与远处贴图共用尺度 | 修窗户部件或排布规则，多栋不同高度/轮廓建筑统一重建，窗户不因楼体拉伸；特色立面仍引用实际资料 |
| 一次打通地下通道 | 共用房间/通道/楼梯/平台/入口及连接接口，真实位置/高程/截面驱动生成；同份空间定义派生可见几何、地面开口、碰撞/落脚面及NPC连通 | 多入口、折弯、上下层和回环共用制作方法；修改台阶/连接规则后相关实例统一更新，玩家和路人可实际通行 |

以上是用户明确举例及当前直接收益最大的复用方式，不是基础架构的完整清单。植被、路灯、街具、角色皮肤/动画、声音和界面部件也按共同定义/实例引用/统一更新审查。当前已有`pixel-surfaces.mjs`共同材质、人物部件/批绘制与字体资源，不重复造另一套；地图和招牌仍有分散字体声明，地下制作仍直接使用五一广场记录，后续先梳理消费者与输入输出，再决定必要改动。

**模型资产的制作链**：实景/尺寸与用途 → 主要形体和模块接口（活动部件确定骨骼、转轴）→ UV/像素密度与共用贴图 → 材质/动画 → 导出与导入 → 游戏内受光、比例、碰撞/通行和动作检查 → 发布共同资产版本并更新引用。Minecraft官方[方块角色教程](https://learn.microsoft.com/en-us/minecraft/creator/documents/entitymodelingandanimation?view=minecraft-bedrock-stable)明确骨骼/转轴、形体、贴图与动画之间的依赖；[Blender UV说明](https://docs.blender.org/manual/en/5.4/modeling/meshes/uv/unwrapping/introduction.html)建议主要拓扑接近稳定后展开UV。保留可编辑源资产；导出格式按现有运行环境确定，不因教程默认安装工具或迁移引擎。

**空间与渲染的职责**：共享模型/材质可批绘制，但GPU实例绘制本身不负责资产版本传播或空间连接；[Three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)用于复用网格/材质减少绘制开销。[Godot导航链接](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationlinks.html)明确链接提供寻路关系，不创建物理通道或自动完成角色运动。因此地下生产能力必须同时生成几何与可走空间，不能仅加几条导航边就算打通。连接机制修正传播到所有采用它的通道，事实位置和高程由各处资料输入。

本轮完成方法学习、源码对照及上述生产顺序修订；没有修改游戏源码，不把制作安排算作已实现能力。后续实施的完成条件包括“共同定义改动确实传播到多个实例”，再验证实际游览与还原；不再用逐处变漂亮或源码文件拆分替代这一条件。

当前代码核对确认：路人主要按计时切换表现，招呼按三种角色固定；问路会计算几何方位并跟踪目标；两处摄影看点有独立主体条件。这些是已实现基础，人物的场所内容和独立动机尚不能由此宣布完成。新知识足以用于下一实际变化，不以继续集齐理论为开工前提。

## 玩家体验及内容安排

玩家可以直接走进世界。方向来自实际道路、建筑轮廓、标识、地形和小地图；目标列表帮助想找下一件事的玩家，随时可忽略或收起。自由探索不锁在任务链后面。抵达一个场所，应有正确入口、可走的空间、值得观察的不同方向、与环境吻合的路人和可拍机位，不能只放一个地标和浮动名称。

摄影让玩家停下、调整视角/画幅/时间、保留所见。真实照片保存后进入相册；旅途里能知道自己发现过、拍过什么。地点标题与可见主体分开；遮挡、反向或未识别主体的照片仍可以保存，但不强行解锁某建筑。相册删除不撤销曾完成的旅程，保存失败不能产生“已收藏”反馈。

路人先作为在真实可行空间活动的市民。靠近后出现交互提示，交谈暂停走动，对话给出符合当前位置和已核实事实的内容；已交谈记录可以回看。后续场所加入有语境的指路/观察/活动，避免整城复制同一段话，也不以“聊天5次”本身替代生活感。

游览目标来自城市内容：看见空间关系、找到真实入口、从多个机位观察、走过经典街区/江岸/山地、留下照片和旅途记录。当前首个操作循环用拍照保存、实际对话、继续走和回看检验系统是否连贯；这不是全市内容量或最终任务设计。远途仍连续可走，长路线要检查沿途可观察内容与返回/保存，不用缩图处理空旷或等待问题。

## 画面、人物、界面和声音共同制作

- 世界尺寸坚持真实地理基准。轮廓/高度/层位/入口不能为好看任意改；方块化与像素贴图表达保持主要形态和辨识特征。
- 材质定义共用单位/像素密度、铺设方向、调色板、受光层次和远距离采样。画面原生清晰渲染，像素属于表面设计，不能把低分辨率模糊当风格。墙面、玻璃、铺地、木材、金属、植被应有区别，避免噪声拼贴。
- 人物用共享的方块比例、骨骼命名、UV/皮肤和动画状态，玩家/路人同一美术家族；走/跑/停/转/跳/交谈/摄影与脚下空间和速度匹配。角色和建筑不靠各自无限新增小方块改善。
- HUD采用方正边框、少量强调色、清楚中文和稳定字号/行高。地址和目标在左上，小地图在右上，快捷栏在下方；标题留在启动页。帮助、统计、设置按需打开，正常游览保留主要视野。图标用统一原创图形，不依赖平台emoji混杂。
- 声音区分脚步表面、城市环境、交互与快门；先检查资源来源与语义再接入。音量控制属于设置。不能保留没有实际声音的装饰音符按钮。

美术制作以真实资料为约束，空间/体量、共用资产、人物/镜头与场景组合联合迭代；先大关系再小细节，在玩家机位与正常游览过程中审查并修正。可读公开工具/格式或用现有工具产出资产；不因发现Blockbench/某引擎就自动安装、迁移。每类资产必须在游戏受光/近远距离/人物附近看过，再推广到全城。

## 系统关系与当前实现决定（R07代码实际状态）

保留Three.js、全市坐标/分块、路网、碰撞和IndexedDB。理由是已查明的核心断点在行为语义、模式所有权及场所/人物/摄影关系，换引擎或重写数据不会直接解决这些问题。现有载体继续按真实资源和运行需求接受检验，不成为永久技术前提。

| 所有权 | 实际落点 | 保持的边界 |
| --- | --- | --- |
| 游玩上下文 | `play-session.mjs` | 主模式/当前面板与可走/可看条件是纯状态，不从网格或DOM推导 |
| 物理输入 | `game-input.mjs` | 键鼠映射唯一，转换上下文释放旧输入；文本编辑不抢字，摄影选项之后F仍工作 |
| 城市看点 | `city-experience.mjs` | 使用真实POI与建筑身份；已定位/准确名称优先但保留未定位记录；关注不完成，保存照片/实际到访独立判定；直线方位不冒充道路路线 |
| 旅途结果 | `journey.mjs` | 成功保存后的照片/人物/可见主体、到访、相遇与关注目标；schema1可读取，schema2增字段，不清原存档 |
| 空间、人物与摄影视图 | `world.mjs`、`character.mjs` | 复用流送与碰撞，游览/摄影取景分离；同行双方保持位置、共同构图/姿势并恢复。旧空间仿真/渲染耦合未为模板目录重写 |
| 协调与界面 | `app.mjs`、`game-hud.mjs`、HTML/CSS | 目的地待接入/有效道路路线分别持有；实际动作→快门证据/PNG→保存事务→旅途→HUD/图鉴/相册；面板停止玩家，其他市民继续活动 |
| 资源与打包 | 本地字体、既有材质/几何、构建/服务脚本 | 场景文字前加载本地字库；原型几何仍共享单位/前向/批容量，不因技能默认就添加GLB或物理库；新资源随包核对 |

摄影异步动作受当前上下文约束，取消后不迟到弹出；PNG恢复当前有效画布。角色批容量与共享预算绑定，超过容量显式报错，不能再静默少画人物部件。

当前玩家流程为自选看点/自由走→观察或问路/合影→独立取景→保存与原图回看→继续游览。远途目的地在广场内也能保留，源道路方位/接入步行/实际规划属于不同状态；走上路网后重新规划，不把玩家移到路上或补虚构连接段。目标可忽略，不复制“拍一张/聊一次/走100米”到整城。真实场所的空间、视觉、人物与摄影继续共同制作；两处摄影看点和近点记录不代表完整全市活动内容。

实际源文件、改前/改后、30项普通操作、94回归、独立构建包与照片原件见[本轮报告](../artifacts/game-redesign-20261016/report.md)、[画面/录像](../artifacts/game-redesign-20261016/index.html)及[交付核验](../artifacts/game-redesign-20261016/delivery-verification.json)。全市还原和正式性能标准未因本批通过而降低。

## R05实际流程形成的进一步安排（2026-10-16）

新依据见[报告](../artifacts/open-game-research-20261016/round05-report.md)和[实际画面](../artifacts/open-game-research-20261016/round05.html)。本次实际补上普通NPC两段对话→合影选择→同框快门→相册大图，以及一次地铁传送→设未知地图目标→沿街发现景点。不能再把这些关系当菜单中几个并列功能，也不能因为参考做了就照抄内容。

已可采用的制作与核对规则落在现有需求中：

| 有实际依据的安排 | 对项目核心问题的帮助 | 实施时要看到的结果 |

| 同一场所的入口/实际可走空间、可观察看点、人物语境和照片结果一起评审 | 减少地标、通用NPC和弹框互相孤立的制作方式；保持真实城市内容 | 正常接近、辨路、停留、交互和回看能对应同一场所；不同走法与遗漏/返回也可成立，不能只排一条演示路线 |
