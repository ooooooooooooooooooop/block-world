## 任务依据与本次纠正

用户要做完整的《我的世界》风格长沙城市游览网页游戏：全长沙景点和连续城市，可从城区一路走到远郊，真实建筑/空间，行走、拍照、路人；后续明确要求参考所给示例的游戏完成度，包括地址、任务、小地图、快捷栏、人物、操作、色彩和精细程度。禁止安排真人。既有全市范围和还原标准保持。

我此前把游戏做成带品牌、营销文字、开发状态和统计卡片的城市展示页面，又用控制器修补、投影尺寸、帧耗时和测试通过当作主要推进。这些工程事实不能证明已理解或完成游戏。随后在未充分调研前又把工作预设成“玩家玩什么、界面为何存在、画面如何统一”三个问题和一份方案，用户再次指出这是自行限缩任务；该预设撤回。

**此前“沿用现有整体路线，继续镜头/庭院小修”的默认顺序撤回。** 已有代码、资料和功能证据可作为待审查资产，不再作为设计正确、架构已定或用户认可的依据。研究结果可以增加问题、改变设计及实现路线；改变用户目标或缩小交付范围仍须由用户决定。

## 游戏设计理论：阅读后的修订

- [MDA原论文](https://www.cs.northwestern.edu/~hunicke/MDA.pdf)：机制、运行中的交互和玩家体验存在因果关系，设计者与玩家观看系统的方向不同。我的错误是从现有功能/渲染往上拼，未经整体行为验证就把功能通过等同于体验进步。它提供分析视角，不是只有三类问题的任务边界，也没有一个可机械保证好玩的公式。
- [MIT游戏设计课程](https://ocw.mit.edu/courses/cms-608-game-design-spring-2008/a2a848079602d24d5baea1aa6b6eb49b_MITCMS_608s08_lec02.pdf)：玩家应能辨认行动与结果的联系，而且结果需要进入更大的游戏关系。对本项目，拍照、交谈、探索及游览记录之间的关系需要研究；单独增加按钮或数字不足以证明这些联系。
- [Steve Swink《Game Feel》出版社介绍](https://www.routledge.com/Game-Feel-Designing-Touch-and-Movement-for-Interactive-Experiences/Swink/p/book/9780123743282)：把操作感作为需要设计的虚拟感受来处理。我之前用速度、角度、平均帧率或P95代替了对动作、空间、接触和反馈的整体审视。这些仍是技术指标，不能直接推出“手感不输示例”。本轮未完整阅读该书，不以找到书名冒充掌握。
- [Beyond the HUD原论文](https://publications.lib.chalmers.se/records/fulltext/111921.pdf)：研究UI与沉浸的关系及设计空间。它针对FPS，不能直接把某一种UI形式或最少面板数宣布为长沙游戏正确答案；需要联系实际玩法判断。

这些理论扩大审查视角，不替用户裁掉任何需求。探索、表达、收集、叙事、挑战或其他体验是否需要，以及具体怎样组合，应继续依据原始目标、参考实际行为及后续取证判断。

## 找到的游戏相关skill及其作用边界

本地可用技能目录没有发现游戏设计/开发专用项。已只读取得[OpenAI公开Game Studio技能包](https://github.com/openai/plugins/tree/main/plugins/game-studio)，阅读总流程、Web Game Foundations、Game UI Frontend、Three WebGL Game、Web 3D Asset Pipeline、Game Playtest及相关HUD/引擎/试玩参考。原文件和获取记录保存在[来源回执](../artifacts/game-design-reset-20261015/game-studio-source-receipt.json)，**没有把资料下载说成插件已经安装或工具已经接入**。

其总流程把玩法、成长/状态、UI、运行架构、资产与试玩放在同一过程中。Game UI Frontend明确反对泛用后台式布局、常驻大标题和大量等权卡片围住游戏场景；这与当前实现的问题直接吻合。Asset Pipeline强调统一单位、朝向、UV/材质、模型结构、碰撞与优化的生产流程。Game Playtest要求从玩家操作、画面和状态变化验证，不能只断言DOM文字和函数结果。

这些是通用工作规范，不能替代游戏设计知识或具体项目判断。比如其3D起步模板默认极少HUD，但用户已经明确指出地址、任务、小地图和快捷栏；**不能借模板再把这些要求藏掉或删掉**。技能的默认引擎、物理库、移动端建议亦不能直接替代本项目的证据和用户约束。

## 对现有项目已经能作出的审查判断

1. “Minecraft风格”没有被转化为涵盖世界、人物、材质、界面、动作和反馈的共同制作依据；以前主要用方块形状/纹理生成器代替完整美术方向。
2. 当前index.html的topbar含品牌、标语和音量/设置；scene-badge公开开发“样板”状态；journey-card常驻统计；controls常驻长操作表。这些来自展示页思路，未围绕玩家游戏状态组织。问题不只是换位置或改圆角。
3. 既有PRD已经记过参考的摄影/图鉴/任务反应，却没有把这些实际关系充分进入实现及验收。既存在了解不够，也存在观察未落实；继续收集截图数量不能自动修复它。
4. 行走、拍照、NPC分别能运行，尚不能证明它们作为游戏系统组合后具有明确、连贯的体验。路人数量/零相交、照片能下载、测试通过只关闭相应技术问题。
5. 现有引擎、文件结构、程序化资产和“下一步修某处细节”的顺序都要重审。现有代码不是唯一可选路径；更换引擎也不会自动补齐设计、美术及内容。
6. 全长沙真实尺度与丰富的可游览内容需要同时研究；长距离穿越成功不能证明沿途有足够的游戏内容。不能用其他游戏的小地图规模来缩减交付城市。
7. 用户提出的界面问题是已发现的症状，不是问题全集。包括世界组织、场景/关卡内容、人物与交互、目标/反馈、视听和制作方式等后续发现，都可进入重审；本记录不把它们固定为封闭清单。
